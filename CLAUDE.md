# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A personal job scanner: scrape PM postings from job boards, drop the ones that
don't fit, read the survivors on a local web page. `README.md` explains the
product decisions; this file is the map for changing it.

## Commands

```bash
uv sync                                  # install; creates .venv

uv run pm-jobs daily                     # scrape → backfill → review, in one go
uv run pm-jobs daily --no-review         # what /pm-jobs-daily runs; leaves judging to the agent
uv run pm-jobs scrape --dry-run          # show every board call, hit nothing
uv run pm-jobs review --dry-run          # deterministic filters only, no model calls, free
uv run pm-jobs review --drops            # what got dropped and why — the tuning feedback loop
uv run pm-jobs review --re-review        # discard all verdicts, re-judge (read/favorite kept)
uv run pm-jobs web                       # the page you actually read, :8000
uv run pm-jobs stats | runs | searches   # store contents, scrape history, config

uv run python tests/run_all.py           # every suite
uv run python tests/smoke_review.py      # one suite — they are plain scripts, run directly
```

No linter, formatter, or type checker is configured. There is no pytest: the
suites are scripts that drive real code paths against a **copy of the real
`pm_jobs.db`**, because that is what caught this project's actual bugs (enum
serialization, redundant re-fetching, a silently uncacheable prompt).

Two consequences. They need `pm_jobs.db` to exist, so they have nothing to do
on a fresh checkout. And `smoke_review.py` / `smoke_web.py` assert the store
has no read jobs, so they fail — pre-existing, unrelated to your change —
whenever the live database has any. **4/6 passing is the current baseline;
check against `git stash` before assuming you broke something.**

Everything resolves paths relative to the working directory. Run from the repo
root, or you silently create a second, empty database.

## The pipeline

```
searches.yaml → scrape.py ──→ store.py (raw_jobs, job_sightings)
                                 │
                    backfill.py ─┤  LinkedIn returns no descriptions; fetch each job page
                                 ↓
preferences.yaml → prefilter.py ─→ review.py ──→ reviewstore.py (job_reviews)
                   (no model)      (model)            │
                                                      ↓
                                        web.py + dedup.py → the page
```

Stages communicate only through SQLite, and each commits before the next runs.
A failure partway through `daily` costs only the stages that hadn't run.

## The four things worth knowing before you change anything

**1. Three kinds of data, three different lifetimes.** Getting these confused
is how you lose something unrecoverable.

| Table | Owner | Regenerable? |
|---|---|---|
| `raw_jobs`, `job_sightings` | the boards | **No** — only by re-scraping, and old postings are gone |
| `job_reviews` | the model | Yes — `review --re-review` rebuilds all of it |
| `job_state` | the user (read, favorite) | **Never regenerated by anything** |

The raw store is append-only: a posting whose text changes gets a *new*
`raw_jobs` row, never an edit, and `payload_hash` excludes volatile fields so
an unchanged re-scrape stores nothing. `job_state` and `job_reviews` are keyed
on `(board, board_job_id)` rather than `raw_jobs.id` precisely because
`raw_jobs.id` is a version — state stored against it would orphan the moment a
board re-lists the job. Schema changes migrate in place (`store._migrate`).

**2. The model answers questions of fact; Python decides what they mean.**
`build_system_prompt` asks what a posting says. `decide()` in `review.py` turns
those answers into keep/drop. Keeping policy out of the prompt is why changing
a rule doesn't require re-reading every posting, and why a verdict is always
consistent with the fields it came from.

Deterministic drops live in `prefilter.py` and run first — they cost nothing
and remove roughly two thirds of a scrape before a token is spent. A question
belongs there only if it is decidable from the text (is this written in Dutch;
does the title match a configured role). Anything with real ambiguity goes to
the model.

**3. Two review backends, one policy.** `run_review()` calls the API;
`export_batch()` / `apply_verdicts()` let the Claude Code session in
`.claude/skills/pm-jobs-daily/SKILL.md` do the reading for free. Both hand
their answers to the same `decide()`, and the instructions and JSON schema are
*generated from `preferences.yaml` and travel inside the export file* — there
is one definition of how a posting gets judged. Each review run records a
`prefs_hash`; `apply_verdicts` refuses a batch judged under different
preferences rather than storing stale verdicts. An agent must never write
`pm_jobs.db` directly — `--apply` is the validation seam.

**4. Duplicates are linked, never merged.** ~7% of postings appear on both
boards. `dedup.py` folds them at display time only; the raw store is untouched
and both URLs stay reachable. `twins()` is why marking one copy read marks the
other — without it a duplicate sits in `unread` forever, which matters far more
in a read/unread list than in a CSV.

## Where to change what

| Want to | Touch |
|---|---|
| Search a new place, term, board, or window | `searches.yaml` only — no Python |
| Change what's dropped or tagged | `preferences.yaml`; the prompt regenerates from it |
| Add a *question the model answers* | 6 places — see below |
| Add a deterministic filter | `prefilter.py`, and return a new `DROP_*` reason |
| Add a CLI command | `cli.py`: a subparser plus an entry in `COMMANDS` |
| Change the page | `web.py` and `pm_jobs/templates/` — server-rendered, no JS, no build |

Adding a field to the model's schema means all six of these, or one backend
drifts from the other:

1. `RESULT_SCHEMA` in `review.py`
2. the matching section in `build_system_prompt`
3. `decide()`, if it changes a verdict
4. the required-fields list in `apply_verdicts`
5. the example verdict in `.claude/skills/pm-jobs-daily/SKILL.md`
6. `tests/smoke_review.py`, `smoke_agent_backend.py`, `smoke_web.py` — each
   builds a fake payload that must satisfy the schema

If the field is user-tunable it also needs parsing in `preferences.py` **and**
inclusion in that module's `material` hash, so verdicts stay attributable to
the preferences that produced them.

## jobspy constraints

`python-jobspy` is pinned to an exact version because `linkedin_details.py`
depends on `LinkedIn._get_job_details`, a private API that can vanish in any
release. That module is the only place allowed to touch jobspy internals, and
it raises `DetailFetchUnavailable` loudly rather than returning empty
descriptions everywhere. Re-check it before unpinning.

- **`distance` is in miles**, not kilometres — jobspy hands Indeed
  `radiusUnit: MILES`.
- **Only `linkedin` and `indeed` work.** Glassdoor and Google are broken
  upstream (they return nothing for a US query either) and the rest are
  regional boards for other markets. `searches.yaml` records the probe results
  and the one-liner to re-test before enabling one.
- LinkedIn search results carry **no descriptions** — hence `backfill.py`,
  which runs as its own pass so it can be throttled and retried without
  touching an already-committed scrape.
- A run asks for the window since the last *successful* run, plus overlap,
  because boards filter on posting date rather than on when a posting became
  visible (`scrape.resolve_window`).

## Conventions

Module docstrings carry the *why* — the measurement, the failure that motivated
the design, the alternative that was rejected. Comments explain decisions, not
mechanics. Match that when you add code; a change that leaves a surprising line
unexplained is incomplete.

Nothing is ever deleted. Drops are stored rows with the rule that dropped them,
so a too-aggressive filter is one query away from being found rather than
invisible.
